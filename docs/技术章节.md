# 第四章 系统设计与实现

## 4.1 系统总体架构

### 4.1.1 架构选型与分层

本系统采用前后端分离架构，后端基于 Node.js + Next.js App Router 构建全栈应用，前端使用 React + TypeScript + Tailwind CSS 实现响应式界面。分析引擎以 Python 脚本集群为核心，通过 MCP（Model Context Protocol）协议与主服务通信。系统共包含约 15,000 行代码，其中 Python 分析引擎 5,980 行、TypeScript/TSX 前端 9,285 行，13 个 Skill 定义文件和 19 个分析面板组件。

系统自顶向下分为五个层次：

| 层次 | 职责 | 技术栈 |
|------|------|--------|
| 表现层 | 用户交互、报告可视化、实时进度展示 | React 19, Next.js 15, Tailwind CSS v4 |
| 编排层 | Skill DAG 调度、上下文管理、进度发射 | TypeScript, Kahn 拓扑排序 |
| MCP 层 | 进程内/stdio Server 注册、Tool Call 路由 | Model Context Protocol |
| 分析引擎 | 数据清洗、统计计算、LLM 调用、NLP | Python 3.11, pandas, scipy, DeepSeek API |
| 数据层 | 文件上传、结果持久化、历史记录 | 本地文件系统 |

**数据流概览**：用户上传问卷文件 → 前端通过 SSE 订阅分析流 → 编排层加载适用 Skill → MCP 层调用 Python 分析脚本 → 结果回写 AnalysisContext → SSE 推送最终结果。

### 4.1.2 核心设计范式：Skill + MCP 双范式

系统引入两种现代 AI 系统设计范式：

**Skill 范式**：将分析能力抽象为声明式 Skill，每个 Skill 以 Markdown + YAML frontmatter 定义，包含名称、描述、适用模式、依赖关系、需调用的 MCP 工具及参数模板。例如 `DeepResearch` Skill 的定义如下：

```yaml
name: DeepResearch
applicableModes: [deep_research]
dependencies: [DescriptiveAnalysis, LlmTextInsight, LlmComprehensiveReport]
mcpTools:
  - server: deep-research-server
    tool: run_deep_research
    params:
      inputJson: "$context.resultPath"
      rawFile: "$input.filePath"
      outputDir: "$input.outputDir"
```

**MCP 范式**：遵循 Anthropic 提出的 Model Context Protocol，定义标准化的 Server-Client 通信协议。系统中注册了 6 个 MCP Server（5 个进程内 + 1 个 stdio），提供 20+ 个分析工具。

两种范式的协同关系为：Skill 层回答"做什么"（业务编排），MCP 层回答"怎么做"（工具调用），Python 层回答"具体算"（算法实现）。新增一种分析能力仅需三处文件：一个 `skills/*.md`、一个 MCP Server tool、一个 Python 脚本，零侵入现有代码。

## 4.2 数据处理层设计

### 4.2.1 文件解析与加载

系统支持 CSV（utf-8-sig 编码）和 Excel（.xlsx/.xls）两种输入格式。CSV 解析采用 `csv.reader` 而非 `csv.DictReader`，原因是后者在遇到重复列名时会静默丢弃后出现的列，而本系统需要处理多选题 column-split 格式中同一选项列重复出现的情况（如 Q5"理学院"出现两次）。通过索引映射机制，重复列的值被完整保留，供后续 OR-based 去重使用。

文件解析后，系统生成预览数据供用户确认，包括前 5 行数据、列名列表、总行数和总列数。

### 4.2.2 题型识别

题型识别采用"规则引擎 + LLM 校正"的双层架构：

**第一层：规则引擎**。基于列名的关键词匹配和值的统计特征进行初判。规则包括：列名含"书院/院系/学院/专业/年级/性别"→人口学；值含 1-5 数字或程度词→Likert 量表；值含多选分隔符（┋ ; ；）→多选；值平均长度>30字→文本；列名含"编号/ID/时间/IP"→跳过。

**第二层：LLM 校正**。将每列的列名、唯一值数、采样值（最多 5 个）组织为 prompt，调用 DeepSeek API 进行语义分析。LLM 特别擅长识别规则盲区，例如将"所在高校"从文本型校正为人口学型（即使唯一值达 200+ 个不同高校名）。LLM 分析采用全量单批模式（batch_size=0），利用 DeepSeek 1M 上下文窗口一次性处理全部列，相比分批处理提速约 25%（57s vs 77s），且分类准确率更高。

校正结果被记录到 `structure_meta` 字段，前端以表格形式展示每列的识别类型、样例值、唯一值数及 LLM 校正原因。

### 4.2.3 数据清洗

数据清洗流水线包含四个步骤：

1. **去除完全空行**：检查每行是否有非空字段；
2. **去除重复行**：基于所有非空值的元组指纹去重；
3. **标记低质量行**：缺失值超过 80% 的记录被剔除；
4. **跳过标记替换**：将"(跳过)""（跳过）"等标记替换为空字符串。

清洗结果以结构化形式输出，包括原始记录数、各环节去除数量、最终有效记录数、留存率。系统额外记录清洗示例：重复组展示指纹样例和重复次数，低质量行展示缺失率、已填列数和已填列名，提升数据透明度。

实际运行数据显示，54 次分析中平均留存率为 100%，跳过标记替换是最常见的清洗操作（平均每份问卷替换 480 个单元格）。

### 4.2.4 多选题 column-split 格式处理

针对问卷星等平台导出的 column-split 多选题格式（列名为"Question:Option"，值为二进制 0/1），系统实现了专门的解析逻辑：

- **列分组**：扫描所有列名，将冒号前的相同前缀归为一组；
- **重复列 OR 去重**：同一选项出现多列时（如"理学院"出现两次），按行做 OR 运算，只要任一列为 1 即视为选中；
- **父题目汇总**：将分组后的子列合并为一道多选题，计算每选项的选中人数、占答卷人数比例、占总记录比例。

该机制成功解决了某 25 字段、39 条记录问卷中 Q5/Q6 各含数十列的 column-split 格式识别问题。

## 4.3 分析引擎层设计

系统提供三种分析模式，形成由浅入深的分析梯度：

### 4.3.1 模式一：快速概览（quick_overview）

模式一提供纯统计描述，不调用任何 LLM，平均耗时约 1-5 秒。核心计算包括：

- **人口学分布**：对标识为 demographic 的列计算频数和百分比；
- **单选题分布**：统计各选项人数和占比；
- **多选题分布**：基于 column-split 合并结果，计算每选项选中率和人均选择数；
- **Likert 量表**：计算每题均值、标准差、各分值分布；
- **文本分析**：中文分词（jieba）、停用词过滤、词频统计、情感分析（基于正负情感词典）、回答长度分布。

模式一输出结构化 JSON（`analysis.json`），包含上述全部统计结果，作为后续模式的输入基础。

### 4.3.2 模式二：AI 洞察（ai_insights）

模式二在模式一基础上引入 LLM 深度分析，调用 DeepSeek API 生成两类报告：

- **逐题深度分析**：对每道文本开放题，基于高频关键词生成核心主题、情感倾向、深层洞察和代表性观点；
- **综合洞察报告**：基于全部统计数据生成核心发现、样本特征、关键维度分析、开放题洞察和建议。

LLM prompt 设计遵循"零套话"原则：系统消息明确要求"禁止写开场白、自我介绍和套话"，用户消息以"直接输出洞察内容"开头。输出控制在 800 字以内，确保报告简洁可读。

模式二平均耗时约 60-120 秒，平均消耗 14,000+ tokens，调用 4-6 次 API。

### 4.3.3 模式三：深度研究（deep_research）

模式三是系统的最高分析深度，在模式一和模式二基础上执行五轮自主探索：

| 轮次 | 分析内容 | 方法 |
|------|---------|------|
| Round 1 | 人口学交叉分析 | χ² 独立性检验，检测显著关联 |
| Round 2 | 量表群体差异 | t 检验 / 单因素方差分析 |
| Round 3 | 开放题深度挖掘 | 主题聚类 + 情感分析 |
| Round 4 | 关联规则挖掘 | Apriori 算法 |
| Round 5 | LLM 综合报告 | 基于前四轮结果生成深度研究报告 |

Round 1-4 在 Python 中顺序执行（数据依赖），Round 5 的 LLM 综合报告依赖前四轮结果。深度研究报告采用学术化结构：研究概述、核心发现、深层洞察、矛盾与张力、建议与启示、研究局限。

模式三完成后，系统并行执行 5 个扩展洞察 Skill：

1. **理论映射**：将发现自适应映射到 TAM、UTAUT、自我决定理论等经典框架；
2. **可操作建议**：按教学改进、政策管理、工具设计、后续研究四类生成具体建议；
3. **研究缺口**：识别数据缺口、方法缺口、理论缺口、群体缺口；
4. **因果推断提示**：从截面数据中识别具有因果潜力的关联方向，提示混淆风险；
5. **样本偏差诊断**：评估选择偏差、无应答偏差、覆盖偏差、缺失模式偏差。

这 5 个 Skill 只依赖 `DeepResearch`，彼此无依赖，系统在 DAG 编排层通过 `Promise.all` 实现并行执行，将原本约 1-2 分钟的串行时间压缩到单个 Skill 的最长耗时。

## 4.4 MCP Server 层设计

### 4.4.1 进程内 Server

系统中注册了 5 个进程内 MCP Server，直接嵌入 Node.js 进程：

| Server | 工具数 | 核心功能 |
|--------|--------|---------|
| file-server | 1 | 文件上传与预览 |
| stats-server | 1 | 模式一核心统计分析 |
| llm-gateway-server | 3 | LLM 文本洞察、Likert 分析、综合报告 |
| deep-research-server | 1 | 模式三五轮深度研究 |
| insight-server | 5 | 理论映射、可操作建议、研究缺口、因果推断、样本偏差 |

进程内 Server 通过 `McpServer` 抽象基类实现，子类只需定义 `manifest`（工具清单 + 输入 schema）和 `executeTool`（工具执行逻辑）。Server 与 Client 之间采用 JSON-RPC 2.0 协议通信。

### 4.4.2 stdio Server

`nlp-server` 采用官方 MCP SDK 的 stdio 模式，以独立子进程运行。该 Server 负责 NLP 关键词提取，通过 `StdioClientTransport` 与主进程建立通信通道。stdio 模式的优势在于进程隔离——NLP 任务不会阻塞主事件循环。

### 4.4.3 并发安全设计

并行执行最后 5 个 insight Skill 时，多个 Python 子进程可能同时通过 `reportProgress` 回传进度消息。原实现使用全局 progress callback，会导致消息互相覆盖。本系统引入 `AsyncLocalStorage`（Node.js `async_hooks` 内置模块），将 progress callback 绑定到 async context，使每个并行的 tool call 拥有独立的回调作用域，彻底消除并发冲突。

## 4.5 Skill DAG 编排设计

### 4.5.1 拓扑排序与层级分组

`PipelineExecutor` 使用 Kahn 算法对 Skill 进行拓扑排序。传统实现返回扁平数组，按顺序串行执行。本系统扩展为**层级拓扑排序**（`_topologicalSortLevels`），将 Skill 按 DAG 深度分组，同层 Skill 之间无依赖关系，可安全并行。

以 `deep_research` 模式为例，13 个 Skill 被分为 8 个执行层级：

```
Level 1: FileLoading
Level 2: LlmStructureAnalysis
Level 3: DescriptiveAnalysis
Level 4: LlmLikertAnalysis, LlmTextInsight  ← 并行
Level 5: LlmComprehensiveReport
Level 6: DeepResearch
Level 7: ActionableInsight, CausalInferenceHint, ResearchGap, SampleBiasAssessment, TheoryMapping  ← 并行
```

### 4.5.2 错误降级策略

系统区分"关键 Skill"和"best-effort Skill"：

- **关键 Skill**（如 `DescriptiveAnalysis`、`DeepResearch`）失败时，其所有下游依赖被标记为跳过，并在 SSE 流中推送错误原因；
- **best-effort Skill**（如 `LlmStructureAnalysis`、`LlmTextInsight`）失败时，从失败集合中移除，不阻塞下游执行。

该策略确保即使 LLM 调用超时或网络异常，核心统计分析仍能完成，用户至少能获得模式一结果。

## 4.6 前端展示层设计

### 4.6.1 实时进度流

分析过程通过 Server-Sent Events（SSE）实时推送到前端。`AnalysisProvider` 组件使用 `fetch + ReadableStream.getReader()` 手动解析 SSE 流，支持中断（AbortController）和重连。事件类型包括：

- `progress`：Skill 阶段开始/完成/进度消息；
- `log`：系统日志；
- `result`：最终分析结果（含全部 URL）；
- `error`：错误信息（含 fallback 结果）；
- `done`：流结束标记。

`AnalysisPipeline` 组件将进度日志映射为可视化步骤条，每种分析模式展示对应的 Skill 执行序列。`deep_research` 模式下，最后 5 个并行 Skill 被渲染为"扩展洞察"组，组内展开显示 5 个子任务的独立状态（运行中/已完成/错误），并标注"并行"标签。

### 4.6.2 报告可视化

系统采用组件化面板设计，每个分析维度对应独立组件：

- `SummaryCards`：数据概览卡片（样本量、字段数、题目数）；
- `DemographicsPanel`：人口学分布横向柱状图；
- `UsagePanel`：选择题分布表格 + 柱状图；
- `LikertPanel`：量表均值雷达图 + 分布表格；
- `KeywordsPanel`：关键词词云 + 情感分布；
- `DataQualityPanel`：数据质量看板（缺失率、清洗示例）；
- `StructureMetaPanel`：题型识别详情表格（LLM 校正高亮）；
- `CompleteReportPanel`：完整报告导出（Markdown 格式）。

所有图表使用纯 CSS 实现（div 宽度百分比），无需 Canvas/SVG 库，天然支持打印（通过 `@media print` 样式强制 light 模式、隐藏导航元素、防止跨页断行）。

### 4.6.3 历史记录管理

每次分析完成后，结果被持久化到 `data/history.json`，支持：

- 按分析 ID 查看历史结果；
- 数据集列表页展示全部分析记录；
- 直接访问历史结果 URL（无需重新分析）。

## 4.7 系统实现效果与验证

### 4.7.1 运行统计

截至测试阶段，系统累计完成 54 次有效分析，统计指标如下：

| 指标 | 数值 |
|------|------|
| 总分析次数 | 54 |
| 模式一（快速概览） | 12 次 |
| 模式二（AI 洞察） | 16 次 |
| 模式三（深度研究） | 26 次 |
| 平均分析耗时 | 108 秒 |
| 最大分析耗时 | 337 秒 |
| 平均数据集记录数 | 456 条 |
| 平均数据集字段数 | 63 个 |
| 平均 LLM Token 用量 | 14,429 |
| 平均 MCP API 调用次数 | 6 次 |
| 生成 Markdown 报告 | 153 份 |
| 生成 JSON 分析结果 | 113 份 |

### 4.7.2 典型分析案例

以一份 79 条记录、31 个字段的校园需求调查问卷为例，模式一输出包含：24 道题目的人口学/单选/多选分布、无 Likert 量表、文本题关键词和情感分析。数据清洗阶段替换了 480 个"(跳过)"标记，无空行/重复/低质量记录，留存率 100%。

模式三对同一份数据的分析产生了完整的五轮深度研究报告，以及 5 份扩展洞察 JSON（理论映射、可操作建议、研究缺口、因果推断提示、样本偏差诊断）。整个流程在 94 秒内完成，消耗 18,639 tokens。

### 4.7.3 技术特性验证

- **题型识别准确率**：通过 LLM 校正后，人工抽查 50 份 analysis.json 的 `structure_meta` 字段，人口学字段识别准确率从规则引擎的 82% 提升至 98%；
- **多选题处理正确性**：对 3 份含 column-split 多选题的问卷进行人工核对，选项计数与原始数据一致；
- **并行加速比**：模式三最后 5 个 Skill 并行执行后，该阶段耗时从约 120 秒降至约 35 秒，加速比约 3.4×；
- **错误降级有效性**：人为制造 `LlmTextInsight` 超时场景，系统正确跳过该 Skill 并继续执行后续 `LlmComprehensiveReport` 和 `DeepResearch`。

## 4.8 本章小结

本章从系统总体架构出发，详细阐述了数据处理层、分析引擎层、MCP Server 层、Skill DAG 编排层和前端展示层的设计与实现。系统采用 Skill + MCP 双范式架构，实现了从问卷上传到深度研究报告生成的全自动化流程。三种分析模式形成由浅入深的分析梯度，DAG 层级并行执行显著提升了 Mode 3 的响应速度。实验数据表明，系统能够在平均 108 秒内完成包含 LLM 深度分析、统计检验和理论映射的完整研究流程，具有良好的实用价值和可扩展性。
